## 1. Installation

### 1a. Add `SwiftL10nCore` as a library dependency

In your app or framework's `Package.swift`:

```swift
dependencies: [
    .package(url: "https://github.com/GRimAce11/SwiftL10n.git", from: "0.1.0"),
],
targets: [
    .target(
        name: "MyApp",
        dependencies: [
            .product(name: "SwiftL10nCore", package: "SwiftL10n"),
        ]
    ),
]
```

Or in Xcode: **File → Add Package Dependencies**, enter the URL, select `SwiftL10nCore`.

### 1b. Install the CLI tool

Build from source:

```bash
git clone https://github.com/GRimAce11/SwiftL10n.git
cd SwiftL10n
swift build -c release
sudo cp .build/release/swiftl10n /usr/local/bin/swiftl10n
```

Verify:

```bash
swiftl10n --version
swiftl10n scan --help
```

## 2. Run your first scan

Point the CLI at your app's source directory:

```bash
swiftl10n scan Sources/MyApp/ --verbose
```

Expected output:

```

  [Text] "Welcome to MyApp" conf:0.99 — HomeView.swift:18
  [Button] "Get Started" conf:0.97 — HomeView.swift:24
  [navigationTitle] "Home" conf:0.99 — HomeView.swift:31
  [Toggle] "Enable notifications" conf:0.95 — SettingsView.swift:12
  [TextField] "Search" conf:0.94 — SearchView.swift:8
  [alert] "Delete account?" conf:0.96 — ProfileView.swift:44
  …

The scan reads source files using SwiftSyntax — it does **not** compile the project, touch the simulator, or require SourceKit.

## 3. Interpret the results

### Confidence score

Every detected string has a `0.0–1.0` confidence score. The score is **deterministic and explainable** — it starts from a rule's base confidence and is adjusted by:

| Factor | Effect |
|---|---|
| Multi-word string | +0.02 |
| Title case | +0.01 |
| Enclosing type ends in `View` / `Screen` | +0.02 |
| Enclosing property is `body` | +0.01 |
| Single character | −0.12 |
| String > 200 chars | −0.25 |
| Contains digits | −0.03 |
| ALL CAPS content | −0.08 |

**Practical thresholds:**

| Range | Interpretation | Action |
|---|---|---|
| 0.95–1.0 | Near-certain UI string | Localise immediately |
| 0.85–0.95 | Very likely UI string | Review, then localise |
| 0.70–0.85 | Probably UI string | Manual review recommended |
| < 0.70 | Uncertain | Investigate individually |

### What gets filtered out

The `FalsePositiveFilter` silently drops these patterns before scoring:

- `https://…`, `ftp://…`, `www.…` — URLs
- `/path/to/file`, `~/Library/…` — File paths
- `arrow.right.circle.fill` — SF Symbol names (dot-separated lowercase)
- `com.example.app`, `org.swift.pkg` — Reverse-DNS identifiers
- `auth_token`, `profile_image_url` — snake_case keys
- `viewModelIdentifier`, `backgroundColor` — camelCase identifiers
- `SOME_FEATURE_FLAG`, `DEBUG_MODE` — SCREAMING_CASE constants
- `Text(verbatim: "…")` — Explicit opt-out

### Interpolated strings

Strings like `"Hello \(name)!"` are **detected but flagged** — they appear in results with `hasInterpolation = true` and a `.warning` diagnostic. They are **excluded from code generation** because they need `String(format:…)` or `LocalizedStringResource` treatment (see [Step 7](#7-handle-interpolated-strings)).

## 4. Generate the Strings enum

```bash
swiftl10n scan Sources/MyApp/ \
    --min-confidence 0.85 \
    --output Sources/MyApp/Generated/Strings.swift
```

The generated file looks like this:

```swift
// Auto-generated by SwiftL10n — do not edit manually.
// Re-run: swiftl10n scan Sources/ --output Sources/MyApp/Generated/Strings.swift

import Foundation

enum Strings {

    enum Home {
        /// "Welcome to MyApp"
        static let welcomeToMyapp = NSLocalizedString(
            "Welcome to MyApp", comment: "Home.welcomeToMyapp"
        )
        /// "Get Started"
        static let getStartedButtonTitle = NSLocalizedString(
            "Get Started", comment: "Home.getStartedButtonTitle"
        )
        /// "Home"
        static let homeNavigationTitle = NSLocalizedString(
            "Home", comment: "Home.homeNavigationTitle"
        )
    }

    enum Settings {
        /// "Enable notifications"
        static let enableNotificationsToggleLabel = NSLocalizedString(
            "Enable notifications", comment: "Settings.enableNotificationsToggleLabel"
        )
        // …
    }
}
```

Add `Sources/MyApp/Generated/Strings.swift` to your `.gitignore` if you want it regenerated on every build, or commit it if you prefer reviewable diffs.

## 5. Use generated code in your app

Replace hardcoded strings one namespace at a time:

```swift
// Before
Text("Welcome to MyApp")
Button("Get Started") { … }
.navigationTitle("Home")

// After
Text(Strings.Home.welcomeToMyapp)
Button(Strings.Home.getStartedButtonTitle) { … }
.navigationTitle(Strings.Home.homeNavigationTitle)
```

Add your localization catalogues (`.strings` files or `.xcstrings`) as normal — `NSLocalizedString` will use them automatically. For a new project with no translations yet, `NSLocalizedString` returns the base-language string unchanged as a safe fallback.

## 6. Automate with an Xcode Build Phase

This runs the scanner before every build and keeps `Strings.swift` in sync automatically.

1. In Xcode, select your target → **Build Phases** → **+** → **New Run Script Phase**
2. Drag the new phase **above** "Compile Sources"
3. Paste this script:

```bash
#!/usr/bin/env bash
set -euo pipefail

# Adjust these paths to match your project layout.
SOURCES_DIR="${SRCROOT}/Sources/${PRODUCT_NAME}"
OUTPUT_FILE="${SRCROOT}/Sources/${PRODUCT_NAME}/Generated/Strings.swift"
SWIFTL10N="${HOME}/.local/bin/swiftl10n"   # or /usr/local/bin/swiftl10n

if [ ! -f "${SWIFTL10N}" ]; then
    echo "warning: swiftl10n not found at ${SWIFTL10N} — skipping string scan"
    exit 0
fi

"${SWIFTL10N}" scan "${SOURCES_DIR}" \
    --min-confidence 0.85 \
    --output "${OUTPUT_FILE}" \
    --quiet

echo "SwiftL10n: regenerated ${OUTPUT_FILE}"
```

4. Under **Input Files**, add:
   ```
   $(SRCROOT)/Sources/$(PRODUCT_NAME)/**/*.swift
   ```
5. Under **Output Files**, add:
   ```
   $(SRCROOT)/Sources/$(PRODUCT_NAME)/Generated/Strings.swift
   ```

Xcode will skip the script if no `.swift` files changed (dependency tracking), making incremental builds fast.

> **Tip:** Gate the script on `$CONFIGURATION` to skip it for test builds:
> ```bash
> [ "$CONFIGURATION" = "Debug" ] || exit 0
> ```

## 7. Handle interpolated strings

SwiftL10n detects `Text("Hello \(name)!")` and emits:

```
warning: "Hello {…}!" — Interpolated string; review before localising (HomeView.swift:22)
```

These require `String(format:…)` or Swift's `LocalizedStringResource` — not a plain `NSLocalizedString` key. Handle them one of two ways:

### Option A — `String(format:…)` (classic)

Add the format string manually to your `.strings` file:

```
/* Home.helloFormat */
"Hello %@!" = "Hallo %@!";
```

Use it in code:

```swift
// Instead of Text("Hello \(name)!")
Text(String(format: NSLocalizedString("Hello %@!", comment: "Home.helloFormat"), name))
```

### Option B — `LocalizedStringResource` (iOS 16+ / macOS 13+)

```swift
// Define once
extension LocalizedStringResource {
    static func hello(_ name: String) -> LocalizedStringResource {
        LocalizedStringResource("Hello \(name)!", comment: "Home.helloFormat")
    }
}

// Use in view
Text(.hello(name))
```

This approach keeps interpolation type-safe and is the direction Apple is pushing in newer APIs.

### Tracking interpolated strings

Filter them programmatically:

```swift
let result = scanner.scan(source: source, filePath: "HomeView.swift")
let needsManualWork = result.detectedStrings.filter(\.hasInterpolation)
```

## 8. Add to CI/CD

### GitHub Actions

Add a step to your CI workflow (`.github/workflows/ci.yml`):

```yaml
- name: Run SwiftL10n
  run: |
    swift run --package-path path/to/SwiftL10n swiftl10n \
      scan Sources/ \
      --min-confidence 0.85 \
      --output /tmp/Strings.swift \
      --quiet
    echo "String scan passed"
```

To **fail the build** when new hardcoded strings are introduced, compare the output to the committed file:

```yaml
- name: Check for new hardcoded strings
  run: |
    swift run --package-path SwiftL10n swiftl10n \
      scan Sources/ \
      --min-confidence 0.90 \
      --output /tmp/Strings.new.swift \
      --quiet

    if ! diff -q Sources/Generated/Strings.swift /tmp/Strings.new.swift > /dev/null 2>&1; then
      echo "error: New hardcoded strings detected. Run swiftl10n locally and commit Strings.swift."
      diff Sources/Generated/Strings.swift /tmp/Strings.new.swift
      exit 1
    fi
```

### Programmatic access for custom tooling

```swift
import SwiftL10nCore

let scanner = StringScanner(minimumConfidence: 0.85)
var totalInterpolated = 0

for fileURL in swiftFiles {
    let source = try String(contentsOf: fileURL)
    let result = scanner.scan(source: source, filePath: fileURL.path)
    totalInterpolated += result.detectedStrings.filter(\.hasInterpolation).count
}

if totalInterpolated > 0 {
    print("warning: \(totalInterpolated) interpolated string(s) need manual localisation")
}
```

## 9. Write custom detection rules

If your project uses a custom view library or internal design system, add rules for it:

```swift
import SwiftL10nCore
import SwiftSyntax

// Detects: DSButton("label") { }
struct DSButtonRule: DetectionRule {
    let name = "DSButtonRule"
    let baseConfidence = 0.94
    let stringArgumentSelector = ArgumentSelector.firstUnlabeled

    func match(in node: FunctionCallExprSyntax) -> DetectionContext? {
        guard node.calledExpression
                .as(DeclReferenceExprSyntax.self)?
                .baseName.text == "DSButton"
        else { return nil }
        return .buttonLabel
    }
}

// Detects: .tooltipLabel("…")
struct TooltipRule: DetectionRule {
    let name = "TooltipRule"
    let baseConfidence = 0.88
    let stringArgumentSelector = ArgumentSelector.firstUnlabeled

    func match(in node: FunctionCallExprSyntax) -> DetectionContext? {
        guard node.calledExpression
                .as(MemberAccessExprSyntax.self)?
                .declName.baseName.text == "tooltipLabel"
        else { return nil }
        return .unknownUIContext(callee: "tooltipLabel")
    }
}

// Compose with the default engine
let engine = RuleEngine(rules: RuleEngine.default.rules + [DSButtonRule(), TooltipRule()])
let scanner = StringScanner(ruleEngine: engine)
```

Register these in a shared factory in your tooling layer so the same engine is used across CLI invocations and unit tests.

## 10. Tune confidence thresholds

| Scenario | Recommended threshold |
|---|---|
| Brand-new greenfield project | `0.80` — be generous early |
| Active production app | `0.85` — good balance |
| Pre-release freeze | `0.90` — high precision, fewer false positives |
| CI gate (fail on new strings) | `0.92` — conservative, avoids noise |

Lower thresholds catch more strings but produce more false positives. If you're seeing too many misses, lower the threshold; if you're seeing too much noise, raise it or add a custom filter:

```swift
let filter = FalsePositiveFilter()  // extend in a future update with project-specific patterns
let scanner = StringScanner(filter: filter, minimumConfidence: 0.85)
```

## 11. Namespace strategies

By default, `NamespaceInferrer` strips common suffixes and uses the file stem:

| File | Namespace |
|---|---|
| `SettingsView.swift` | `Settings` |
| `OnboardingScreen.swift` | `Onboarding` |
| `ProfileViewController.swift` | `Profile` |
| `HomePageController.swift` | `HomePage` |
| `LoginController.swift` | `Login` |

**Feature-based organisation** (recommended): keep one view per file named after its screen. The inferrer handles the rest.

**Collision handling**: if two files resolve to the same namespace, `NamespaceInferrer` appends a numeric suffix (`Settings`, `Settings2`). Avoid this by naming files distinctly.

**Forcing a namespace** (future feature): you can drive custom namespaces programmatically:

```swift
let inferrer = NamespaceInferrer()

// Override: treat all onboarding files as one namespace
let onboardingFiles: [(String, [DetectedString])] = [
    ("WelcomeView.swift", welcomeResult.detectedStrings),
    ("PermissionsView.swift", permissionsResult.detectedStrings),
]
let merged = onboardingFiles.flatMap(\.1)
let namespace = Namespace(name: "Onboarding", sourceFile: "WelcomeView.swift", strings: merged)
```

## 12. Incremental migration playbook

For a large existing codebase, migrate screen by screen rather than all at once.

### Week 1–2: Audit

```bash
# Get the full picture — don't filter yet
swiftl10n scan Sources/ --verbose > /tmp/l10n-audit.txt
wc -l /tmp/l10n-audit.txt
```

Identify the highest-traffic screens first (Settings, Onboarding, Home).

### Week 3–4: Generate and integrate one namespace

```bash
swiftl10n scan Sources/MyApp/Settings/ \
    --min-confidence 0.85 \
    --output Sources/MyApp/Settings/Strings+Settings.swift
```

Replace strings in `SettingsView.swift` and its child views. Add a unit test:

```swift
func testSettingsStringsExist() {
    XCTAssertFalse(Strings.Settings.settingsNavigationTitle.isEmpty)
    XCTAssertFalse(Strings.Settings.deleteAccountButtonTitle.isEmpty)
}
```

### Week 5+: Roll out remaining screens

Repeat for each screen. After full coverage, enable the CI gate.

### Do not migrate these yet

- Interpolated strings (`hasInterpolation = true`) — handle separately with `String(format:…)` or `LocalizedStringResource`
- Debug/logging strings — they should never have been UI strings, ignore them
- Low-confidence results (< 0.70) — manual review required

## 13. Troubleshooting

### "String I expect to be detected is missing"

1. Check if it's filtered: `FalsePositiveFilter().exclusionReason(for: "your string")`
2. Check if the call site is supported (see the [detection rules table](../README.md#detection-rules))
3. Check the confidence threshold — run with `--min-confidence 0.0` to see everything
4. If it's a custom view (`DSButton`, `FormField`, etc.) — write a custom rule (see [Step 9](#9-write-custom-detection-rules))

### "String I DON'T want is being detected"

1. Look at the `ExclusionReason` — the filter may need a new pattern
2. Raise `--min-confidence` to filter out low-confidence noise
3. Use `Text(verbatim: "…")` to explicitly opt out at the call site
4. If it's a systematic pattern (e.g. all strings in `AnalyticsManager.swift`), add a custom `FalsePositiveFilter` subclass

### "Generated Strings.swift is empty"

- Check that `--min-confidence` isn't set too high
- Verify the source path is correct and contains `.swift` files
- Run without `--quiet` to see diagnostic output

### "Build Phase script adds too much to build time"

Set `Based on dependency analysis = Yes` and define proper Input/Output files (Step 6). Xcode will skip the script when no `.swift` source files changed.

### "SF Symbol names are being detected"

`FalsePositiveFilter` excludes any `word.word.word` all-lowercase pattern. If your SF Symbol names are being detected, they likely contain uppercase letters — this is a bug; please file an issue.

### Swift 6 concurrency warnings in my project

`StringScanner`, `RuleEngine`, and all model types are `Sendable`. Use them freely across actor boundaries:

```swift
@MainActor
func scanInBackground() async {
    let scanner = StringScanner()   // Sendable — safe to capture
    let result = await Task.detached {
        scanner.scan(source: source, filePath: path)
    }.value
    self.results = result.detectedStrings
}
```
